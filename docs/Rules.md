# RULES --- Claude Project Operating Rules

## 1. Core Principle

Build the system as an **automated, generalizable disaster-mapping
pipeline**, not as a Trishuli-only demo.

The judges can choose the area and date live.

Never hardcode the expected answer.

---

## 2. Source-of-Truth Hierarchy

### Tier 1 --- Mandatory challenge requirements

Treat the official Track B problem statement as authoritative for:

- allowed/forbidden inputs
- judging criteria
- output requirements
- required attribution
- submission requirements
- case-study requirements
- ethical/responsibility requirements.

### Tier 2 --- Project decisions

Use this project's PRD, Design, Phases, and Memory files for agreed
implementation decisions.

### Tier 3 --- Technical references

Use official documentation and reliable technical references when
implementation details are not defined by the challenge.

### Tier 4 --- Model suggestions

Claude may suggest alternatives, but must label them as suggestions.

Never silently convert a suggestion into a requirement.

---

## 3. Forbidden Data Rule

Never use the following as an input to the actual mapping pipeline:

- Copernicus EMS damage maps
- UNOSAT damage maps
- published damage maps
- post-event OSM edits
- any external source that already supplies the answer.

These can be used only for validation/checking where the challenge
allows.

If uncertain whether a source is allowed:

**STOP and flag the uncertainty. Do not silently use it.**

---

## 4. Generalization Rule

No hardcoded:

- coordinates
- flood masks
- settlement lists
- road damage lists
- damage counts
- thresholds selected only for the final demo scene.

The system must operate from:

```text
AOI + event date
```

---

## 5. AI Grounding Rule

The LLM must never invent:

- counts
- distances
- percentages
- affected areas
- road lengths
- settlement names
- hospitals
- damage numbers.

All numerical and factual result values must come from structured
outputs generated by the deterministic pipeline.

Preferred architecture:

```text
GIS/remote-sensing engine
        ↓
validated JSON
        ↓
LLM
        ↓
natural-language answer
```

If a requested value is unavailable:

> "The system does not have a verified value for this metric."

Do not guess.

---

## 6. Data Contract Rule

Every major module must produce a documented machine-readable output.

Suggested formats:

- GeoTIFF for rasters
- GeoJSON for spatial vector outputs
- JSON for statistics/metadata.

Modules must not depend on undocumented variables or manual copy-paste.

---

## 7. CRS Rule

Every spatial file must have an explicit CRS.

Before:

- intersection
- distance
- length
- area
- graph geometry operations

verify CRS compatibility.

Never calculate geographic distance/length directly in
latitude/longitude degrees when a projected CRS is required.

---

## 8. Satellite Pair Rule

For before/after change detection, prefer:

- same satellite/product family
- same acquisition mode
- same polarization
- same relative orbit/track
- comparable geometry
- suitable temporal relationship.

Do not compare arbitrary Sentinel-1 scenes simply because they cover the
same area.

For the Trishuli case, the challenge recommends same-track images about
12 days apart.

---

## 9. SAR Processing Rule

Never assume raw SAR values are directly comparable.

The pipeline must account for the required processing stage, including
where appropriate:

- calibration/backscatter conversion
- thermal/noise handling
- speckle treatment
- terrain correction/orthorectification
- nodata masking
- alignment.

If using a Copernicus processed product/service that already performs
part of this chain, document exactly what has already been done.

---

## 10. Terrain Rule

Mountain terrain is a major source of false detections.

Use DEM-derived constraints where appropriate.

Do not label a dark radar region as flood solely because it is dark.

Check:

- terrain
- radar geometry
- water plausibility
- proximity/relationship to drainage
- quality masks.

---

## 11. Building Damage Language Rule

At approximately 10 m Sentinel resolution, do not claim:

- "house destroyed"
- "building collapsed"

based solely on raster intersection.

Use:

- "estimated affected building"
- "building intersects detected affected area"
- "likely hit"

unless independent evidence is explicitly permitted and available.

---

## 12. OSM Rule

Use a **pre-event OSM snapshot**.

Do not query current OSM and assume it represents the pre-event state.

The challenge specifies the ohsome API for this purpose.

Document the snapshot date.

---

## 13. Road Connectivity Rule

"Cut off" means:

> no remaining mapped road path to the selected destination.

It does NOT automatically mean:

- the village has no communication
- people cannot walk out
- the village is completely inaccessible
- helicopter access is required.

Always phrase results precisely.

---

## 14. Validation Rule

Use validation data only after producing the system result.

Correct:

```text
Our algorithm → output
             ↓
         compare with
             ↓
       allowed reference
```

Incorrect:

```text
reference map
    ↓
algorithm
    ↓
matching answer
```

Never tune the algorithm by looking at the validation answer and then
claiming independent evaluation.

---

## 15. Testing Rule

Every major feature must be tested on:

1.  primary Trishuli case
2.  at least one additional scene/area before final submission.

If a feature only works on Trishuli, mark it as overfit/not
production-ready for judging.

---

## 16. No Fake Success Rule

Never hide:

- failed scenes
- missing data
- poor segmentation
- invalid geometries
- no suitable satellite pair
- OSM gaps
- disconnected graph due to bad data
- processing errors.

Display meaningful warnings.

---

## 17. Implementation Rule

Prefer the simplest method that satisfies the rubric.

Do not introduce:

- unnecessary microservices
- complex MLOps
- large model training
- Kubernetes
- distributed processing

unless they solve a demonstrated problem.

15 days is the constraint.

---

## 18. AI Component Rule

Recommended choice:

**Situation-report copilot**

Do not start training a segmentation model unless the core deterministic
pipeline is already working and the team has enough time/GPU.

If segmentation is attempted, it must be treated as an additional model
component, not as permission to skip the required geospatial pipeline.

---

## 19. UI Rule

Dashboard should prioritize:

1.  map clarity
2.  correct layers
3.  understandable statistics
4.  traceability
5.  usability

Do not sacrifice backend correctness for visual effects.

---

## 20. Code Quality Rule

Each completed module should include:

- clear file naming
- docstrings/comments where useful
- configuration instead of magic numbers
- error handling
- logs
- a small test or validation example.

Avoid giant single Python files.

---

---

## 22. Dependency Rule

Before adding a library:

1.  explain why it is needed
2.  check compatibility
3.  prefer maintained/common packages
4.  update dependency file
5.  test installation.

---

## 23. Secret Rule

Never hardcode:

- API keys
- OAuth secrets
- LLM keys
- passwords.

Use environment variables.

Example:

```text
.env
```

must be excluded from Git.

Provide:

```text
.env.example
```

with placeholder names.

---

## 24. Execution Rule

After every implementation task:

1.  run the relevant code
2.  inspect the output
3.  fix errors
4.  run the relevant test
5.  update Memory.md
6.  report what changed
7.  report remaining limitations.

Do not claim completion merely because code was written.

---

## 25. Memory Rule --- MANDATORY

After every completed execution/task:

**Update Memory.md.**

Record:

- what was implemented
- files changed
- tests run
- outputs
- known issues
- decisions made
- next recommended task.

Memory.md is the project's persistent implementation state.

---

## 26. Claude Completion Rule

When a task is successfully completed:

- return a concise summary
- list modified/new files
- provide test/result status
- update Memory.md
- return a properly foldered ZIP of the project when files have been
  created or modified.

The ZIP must preserve the intended repository structure.

---

## 27. Do Not Overwrite Working Code Blindly

Before major changes:

- inspect current implementation
- understand dependencies
- preserve working functionality.

Prefer small patches over unnecessary rewrites.

---

## 28. User Understanding Rule

The user wants to understand what is being built.

For important technical decisions, Claude should explain:

- what the component does
- why it is needed
- what alternatives exist
- why the selected approach is suitable for a 15-day hackathon.

Do not dump unexplained code.

---

## 29. Honest Status Labels

Use:

- `PLANNED`
- `IN PROGRESS`
- `IMPLEMENTED`
- `TESTED`
- `BLOCKED`
- `OPTIONAL`
- `KNOWN LIMITATION`

Do not mark something `DONE` unless it has been executed/tested where
execution is applicable.

---

## 30. Safety and Responsibility

Do not include victim images or exploitative disaster imagery.

Treat the recent disaster respectfully.

Always state that the project is an educational prototype and not an
operational rescue tool.
